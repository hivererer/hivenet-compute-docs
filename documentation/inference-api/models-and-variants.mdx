Hivenet Inference API uses a curated model catalog. Each model can have one or more **variants** that define how that model is served.

The production console is the source of truth for what you can deploy now. Model and variant availability depends on the location you choose first.

## Model versus variant

A **model** is the model family or checkpoint you want to use. Its catalog card can include:

- A short description
- Capability tags
- A starting hourly price

A **variant** is a deployable serving configuration for that model. Depending on the model, a variant can define or display:

- GPU type and GPU count
- Quantization
- Context window
- Expected request capacity
- Time to first token
- Inter-token latency
- Output speed
- License
- Current hourly price

You select a variant before choosing the number of replicas.

## Choose the location first

The current production flow starts with location.

The selected location determines which models and variants can be provisioned. A location can be marked **Sold out** when there is no capacity for a new endpoint.

The location screen also displays a data-handling notice. Read that notice before deploying because it describes how prompts and responses are handled for the selected location.

## Choose for the workload

Start with what your application needs rather than automatically choosing the largest model.

Consider:

- **Task type:** chat, document Q&A, instruction following, structured output, tool calling, multimodal input, or other capabilities shown in the catalog
- **Context needs:** how much input and conversation history the endpoint needs to handle
- **Latency:** whether people wait interactively for responses
- **Throughput:** how much request capacity you need
- **Cost:** the variant rate multiplied by the number of replicas you run

The model cards and tags in the console are there to help narrow the catalog before you inspect a variant in more detail.

## Context window

The context window is the token space available to the served model for input and generated output.

A larger context window can support longer prompts and conversations, but it does not guarantee the same latency or throughput as a shorter request. Long prompts require more prefill work and can take longer before the first output token is returned.

Use the context value shown for the production variant you are actually deploying.

## How Hivenet characterizes models

Hivenet maintains a newer benchmark and model-characterization set for the serving artifacts it evaluates. It separates model characteristics from the live self-service catalog so model data can evolve without implying that every characterized artifact is currently orderable in every location.

The current characterization set includes:

| Model profile | Characterized serving artifact | Context characterized | Workload shapes tested |
| --- | --- | --: | --- |
| **Gemma 4 26B-A4B IT** | HivenetQuant NVFP4 W4A16 hybrid | 262,144 tokens | Chat, agentic, async, async multimodal |
| **Gemma 4 31B IT** | HivenetQuant NVFP4 W4A4 mixed precision | 262,144 tokens | Chat, agentic, async, async multimodal |
| **GPT-OSS 20B** | Native OpenAI MXFP4 | 131,072 tokens | Chat, agentic, async |
| **Qwen3.6 27B** | HivenetQuant NVFP4 W4A4 | 262,144 tokens | Chat, agentic, async, async multimodal |
| **Qwen3.6 35B-A3B** | HivenetQuant NVFP4 W4A16 hybrid | 131,072 tokens certified | Chat, agentic, async, async multimodal |
| **Qwen3.8 27B** | HivenetQuant NVFP4 W4A4 | 262,144 tokens | Chat, agentic, async, async multimodal |

For Qwen3.6 35B-A3B, the underlying checkpoint has a larger native context ceiling, but the current benchmark certification covers requests up to 131,072 tokens. We use the certified range rather than turning the larger native limit into a performance claim.

<Warning>
  This table describes model-characterization work. It is **not** a list of models guaranteed to be available in the production console. Check the live model and variant cards for the endpoint you are creating.
</Warning>

## What the workload labels mean

The benchmark uses several repeatable request shapes so capacity and latency are not reduced to one misleading number:

- **Chat:** Short interactive requests.
- **Agentic:** Longer requests designed to represent reasoning and tool-oriented workflows.
- **Async:** Batch-style text work where interactive first-token latency is less important.
- **Async multimodal:** Batch work that combines visual input with text on models characterized for multimodal serving.

A model appearing in one of these benchmark categories means Hivenet measured that serving artifact against that request shape. It does not mean the benchmark proves that model gives the best answers for that use case.

<Info>
  The benchmark measures serving capacity and latency, not model quality. Test candidate models with your own prompts and data before choosing one for production.
</Info>

## Quantization and GPU configuration

Hivenet can characterize quantized serving artifacts to reduce memory use and improve serving efficiency. Some are produced by **HivenetQuant**, while GPT-OSS 20B uses OpenAI's native MXFP4 release in the current characterization set.

The variant card in the console shows the quantization and GPU configuration for the endpoint you can actually deploy. Treat those live details as the production configuration rather than assuming they match a benchmark artifact exactly.

## Request capacity and replicas

The production variant section can show an approximate requests-per-minute figure alongside the replica selector.

Treat that figure as a planning estimate for the displayed serving configuration rather than a universal limit for every possible prompt. Real request cost varies with input length, output length, concurrency, modality, and the model itself.

The production product uses a fixed replica count. More replicas increase available serving capacity and hourly cost.

<Note>
  Autoscaling is not available in the current production version.
</Note>

## Live availability comes from the console

The console initially shows a curated set of model cards and provides **All models** to browse the wider catalog.

Do not rely on a static model list in these docs to decide what can be deployed. Models, variants, prices, GPUs, context settings, and regional capacity can change independently of documentation updates.

<Warning>
  Check the console for the model, GPU configuration, quantization, context window, price, and replica capacity you can deploy now.
</Warning>

## Existing endpoints keep their serving configuration

An endpoint keeps the model and serving configuration selected when it was created unless you explicitly change a supported setting such as replica count.

The model name used in API requests is attached to the endpoint. Use the exact `model` value shown in its generated quick-start snippet.
