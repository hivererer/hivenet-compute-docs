Hivenet Inference API uses a curated model catalog. Each model can have one or more **variants** that define how that model is served.

The production console is the source of truth for what you can deploy now. Model and variant availability depends on the location you choose first.

## Model versus variant

A **model** is the model family or checkpoint you want to use. Its catalog card can include:

- A short description
- Capability tags
- A starting hourly price

A **variant** is a deployable serving configuration for that model. Depending on the model, a variant can define or display:

- GPU type and GPU count
- Quantization
- Context window
- Expected request capacity
- Time to first token
- Inter-token latency
- Output speed
- License
- Current hourly price

You select a variant before choosing the number of replicas.

## Choose the location first

The current production flow starts with location.

The selected location determines which models and variants can be provisioned. A location can be marked **Sold out** when there is no capacity for a new endpoint.

The location screen also displays a data-handling notice. Read that notice before deploying because it describes how prompts and responses are handled for the selected location.

## Choose for the workload

Start with what your application needs rather than automatically choosing the largest model.

Consider:

- **Task type:** chat, document Q&A, instruction following, structured output, tool calling, multimodal input, or other capabilities shown in the catalog
- **Context needs:** how much input and conversation history the endpoint needs to handle
- **Latency:** whether people wait interactively for responses
- **Throughput:** how much request capacity you need
- **Cost:** the variant rate multiplied by the number of replicas you run

The model cards and tags in the console are there to help narrow the catalog before you inspect a variant in more detail.

## Context window

The context window is the token space available to the served model for input and generated output.

A larger context window can support longer prompts and conversations, but it does not guarantee the same latency or throughput as a shorter request.

Use the context value shown for the production variant you are actually deploying.

## Quantization and GPU configuration

The selected variant can show the GPU and quantization used to serve the model.

These are part of the managed serving configuration. You do not configure the underlying model server or GPU settings yourself after deployment.

## Request capacity and replicas

The variant section can show an approximate requests-per-minute figure alongside the replica selector.

Treat that figure as a planning estimate for the displayed serving configuration rather than a universal limit for every possible prompt. Real request cost varies with input length, output length, and workload shape.

The production product uses a fixed replica count. More replicas increase available serving capacity and hourly cost.

<Note>
  Autoscaling is not available in the current production version.
</Note>

## Current production catalog

The production Figma shows the catalog containing models from families including Falcon and Mistral, with **All models** available to browse beyond the initial cards.

Do not rely on a static list in these docs to decide what can be deployed. Models, variants, prices, GPUs, and regional capacity can change independently of documentation updates.

<Warning>
  Check the console for the model, GPU configuration, quantization, context window, price, and replica capacity you can deploy now.
</Warning>

## Existing endpoints keep their serving configuration

An endpoint keeps the model and serving configuration selected when it was created unless you explicitly change a supported setting such as replica count.

The model name used in API requests is attached to the endpoint. Use the exact `model` value shown in its generated quick-start snippet.
