Hivenet Inference API uses the same prepaid organization credit balance as Compute.

You pay for the model-serving capacity that is running. The console shows the current cost before deployment and updates it as you change fixed or autoscaling capacity.

## Fixed-capacity billing

With autoscaling turned off, the deployment keeps a fixed number of replicas running.

The displayed hourly cost follows the selected model variant and the number of running replicas. Increasing the fixed replica count increases the current cost; reducing it lowers the cost after the change takes effect.

Before deployment, **Review your setup** also shows estimated cost over 24 hours and one week.

## Autoscaling billing

Autoscaling separates your baseline capacity from temporary burst capacity:

- **Reserved replicas** stay running and are billed continuously while the deployment is active.
- **Burst replicas** are best effort and are billed only while they are active.

The console shows the current prices and estimates for the selected model variant. Use those live values rather than relying on an old screenshot or saved estimate.

<Info>
  Burst capacity can reduce the need to keep peak capacity running all the time, but it is not guaranteed when the region has no spare infrastructure.
</Info>

## When charging starts

A new or restarted deployment enters **Starting** while Hivenet prepares serving capacity.

The V2 deployment flow states that starting a model can take up to 10 minutes and that charges begin once the model is running.

For autoscaling deployments, additional burst charges begin only when burst replicas become active.

## When charging changes

The current cost can change when you:

- Increase or reduce a fixed replica count
- Change the Reserved count
- Change the Burst limit
- Autoscaling starts or removes burst replicas
- Stop or start the deployment

The deployment details show current cost information together with replica activity so you can see how the active serving configuration relates to spend.

## When charging stops

Stopping a deployment tears down its serving replicas. Charges stop once the running capacity has shut down.

Terminating a deployment also stops charges once termination is complete.

<Warning>
  Disabling or revoking an Inference API key does not stop a deployment. Its serving capacity stays online and continues to use credits until you stop or terminate it.
</Warning>

## Stopped deployments

A stopped deployment keeps its configuration but does not keep serving replicas running.

You can start it again later if enough organization credits and regional capacity are available. Charges resume when serving capacity comes back online.

Stopping is useful when you expect to reuse the deployment but do not need the endpoint continuously.

## Organization credits

Inference API and Compute resources draw from the same organization balance.

If the organization does not have enough credits to deploy or start a model, the console shows a warning and an **Add credits** path before the action proceeds.

If you cannot manage the organization balance yourself, ask the organization Owner to add credits.

See [Billing information](/documentation/account-billing/billing-info) for payment methods, auto top-up, invoices, and organization billing roles.

## Monitor spend

The Inference API page can show:

- Spend over the last 24 hours
- Current hourly cost for each deployment
- Cost so far in deployment details
- Replica activity that can explain autoscaling changes

You can also use the main Compute billing views to understand the shared organization balance.

See [Track organization spending in real time](/documentation/account-billing/track-costs-real-time).

## Cost is based on serving capacity

Inference API is not billed purely by the number of tokens in each request. The serving capacity you keep running is what drives the deployment cost.

That means sending fewer requests does not automatically reduce the cost of a fixed deployment. With autoscaling enabled, burst replicas can scale down when demand falls, but your Reserved replicas remain running until you change the configuration or stop the deployment.
