The Compute API uses standard HTTP status codes and a consistent JSON error envelope.

## Error response format

Errors use this structure:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Not found.",
    "request_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"
  }
}
```

| Field | What it means |
| :-- | :-- |
| `error.code` | Stable machine-readable error code. Use this in client logic. |
| `error.message` | Human-readable explanation. Don't branch on this text. |
| `error.request_id` | Identifies the request in Hivenet logs. Include it when contacting Support. |

<Warning>
  Client logic should branch on `error.code`, never on `error.message`. Messages can change without changing the underlying error condition.
</Warning>

## Common error codes

| Status | Code | Meaning |
| :-- | :-- | :-- |
| `400 Bad Request` | `VALIDATION_ERROR` | A parameter or request value is invalid. |
| `401 Unauthorized` | `UNAUTHORIZED` | The API key is missing or invalid. |
| `403 Forbidden` | `FORBIDDEN` | The resource exists but the account cannot access it. |
| `404 Not Found` | `NOT_FOUND` | The requested resource does not exist. |
| `409 Conflict` | `CONFLICT` | A lifecycle action conflicts with the current state, credit is insufficient, or instance creation has no capacity for the selected preset. |
| `429 Too Many Requests` | `TOO_MANY_REQUESTS` | The rate limit was exceeded. |
| `500 Internal Server Error` | `INTERNAL_ERROR` | The server could not complete the request. |
| `503 Service Unavailable` | `INTERNAL_ERROR` | No host currently has enough capacity for the requested start operation. |

## Handle creation errors

`POST /instances` returns `409 CONFLICT` if capacity is unavailable, a prepaid account lacks credit for one hour, or the preset changed during creation. These failures do not create an instance. A no-capacity response has no `Retry-After` header; choose another compatible preset or try later.

Register an SSH public key before creating an instance. A `404` can also mean that the preset or image is missing or that the preset’s location does not offer that image.

## Handle 409 conflicts

`409 Conflict` uses error code `CONFLICT`, but it can have more than one cause.

- **Start:** the instance is terminating or terminated, or the account does not have enough credit.
- **Stop:** the instance is terminating or terminated.
- **Terminate:** the instance is already terminated.

The error message does not distinguish these cases. Fetch the current instance state first. If a start request conflicts even though the instance can be started, check the account balance before retrying.

<Steps>
  <Step title="Fetch the current state">
    Call [`GET /instances/{id}`](/public-api/endpoints/get-instance).
  </Step>
  <Step title="Check what blocked the action">
    Use the instance state to identify lifecycle conflicts. For start requests, also check whether the account has enough credit.
  </Step>
  <Step title="Retry only when the cause is resolved">
    Wait for a valid state transition or add credit as needed before sending the action again.
  </Step>
</Steps>

## Handle rate limits

Each API key has a limit of **60 requests per minute per endpoint**. Calls to one endpoint do not consume another endpoint's budget. Different keys have separate budgets, including when callers share a network address.

Calls to `GET /instances/{id}/metrics` share one budget across all instance IDs. For example, refreshing 20 instances every 15 seconds requires 80 requests per minute and exceeds the limit. Cache results and stagger polling across instances.

A `429 Too Many Requests` response includes a `Retry-After` header. Wait that many seconds before retrying.

```text
Retry-After: 60
```

Leave room below the limit for other requests using the same key. Continue handling `429` dynamically; shared service protection can also throttle requests. Release testing observed `Retry-After: 60`. Use the delay returned by the request. Do not depend on undocumented rate-limit headers.

## Handle server errors

A `500` response uses the generic message:

```json
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "An internal error occurred.",
    "request_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"
  }
}
```

The message is intentionally generic. Use `error.code` for program logic and keep `request_id` for troubleshooting.

For temporary read errors, retry after a short delay. Before retrying a state-changing request, check whether it completed. If the problem continues, contact Support with the `request_id`.

## Handle temporary capacity errors

A start request can return `503 Service Unavailable` when no host currently has enough free capacity for the instance's preset. The body uses `INTERNAL_ERROR` rather than a separate capacity error code.

Retry with backoff, or choose a compatible preset in another region. This is a temporary capacity condition rather than a problem with the request itself.

## Retry safely

`POST /instances` is not idempotent. Every successful call creates a separately billed instance, including repeated calls with the same name and body. After a lost connection or a `500`, `503`, or `504`, check [List instances](/public-api/endpoints/list-instances) before submitting another create request.

Registering the same SSH public key again creates another key record with a new ID. Save and reuse the ID returned by the first successful registration.

| Request type | Retry guidance |
| :-- | :-- |
| Read-only requests | Usually safe to retry after a short delay. |
| `400` | Fix the request before retrying. |
| `401` or `403` | Fix authentication or access before retrying. |
| `409` | Check the latest instance state and, for start requests, the account balance before retrying. |
| `429` | Wait for `Retry-After`. |
| `500` | For reads, retry after a delay. For writes, check the outcome first; contact Support if it remains unclear. |
| `503` | For start capacity errors, retry with backoff. For create, check whether the instance exists first. |
| `504` on create | Check the instance list before retrying. |

<Danger>
  Before retrying a destructive action such as terminate, fetch the instance state and confirm the action is still needed.
</Danger>

## What to include when asking for help

Include:

- The endpoint and HTTP method
- The HTTP status
- `error.code`
- `error.request_id`
- A redacted request if useful

Never include your API key.
