Use this page to track changes to the Compute API that may affect scripts, tools, or integrations.

## Current API version

Production base URL:

`https://api.hivecompute.ai/v1`

Staging base URL:

`https://staging-api.hivecompute.ai/v1`

The endpoint reference covers instance lifecycle, logs, usage metrics, regions, and hardware presets.

## Latest changes

<Update label="Unreleased" description="Instance response corrections">
  ## Instance response corrections

  These changes are pending release. They affect list, get, start, stop, and terminate responses.

  <Warning>
    This update changes response formats used by existing integrations. Update clients that rely on numeric enum values, timestamp objects, action-response `id`, or undocumented fields.
  </Warning>

  **Response changes**

  - `status`, `guest_ready`, and `termination_reason` use names instead of numeric enum values. For example, `status: 3` becomes `status: "RUNNING"`.
  - `status` includes `PAUSED` for a running instance affected by a host outage. Billing is suspended until the host returns.
  - `guest_ready` uses `READY`, `DEGRADED`, or `UNKNOWN`. It reports VM guest-agent readiness; containers return `UNKNOWN`. It does not change status or billing.
  - `termination_reason` is `null` unless the instance is `TERMINATING` or `TERMINATED`. During or after termination, it uses `USER_INITIATED`, `CREDIT_EXHAUSTION`, or `UNKNOWN`.
  - `started_at` and `terminated_at` use ISO 8601 strings instead of objects containing `seconds` and `nanos`. Unset timestamps return explicit `null`.
  - Start, stop, and terminate normally return the same instance fields as GET, using `instance_id` instead of `id`. When the updated details cannot be read, they return `201` with only `instance_id`.
  - Responses omit undocumented fields, including owner details, host identifiers, and internal deployment and billing fields.

  **Update your integration**

  Compare enum fields with their documented names, parse timestamps as strings or `null`, and use `instance_id` from action responses. Handle a successful response containing only that ID by polling `GET /instances/{id}`. Don't repeat an accepted action because other fields are missing.

  See [Work with instances](/public-api/work-with-instances) for the field meanings and [retry guidance](/public-api/handle-errors-and-rate-limits#handle-a-successful-response-with-only-an-instance-id).
</Update>

<Update label="October 29, 2026" description="Compute v1.38">
  ## Instance usage metrics

  Added [`GET /instances/{id}/metrics`](/public-api/endpoints/get-instance-metrics) for instance usage time series. The `range` parameter is required and accepts `1h`, `6h`, `24h`, or `7d`, without case sensitivity.

  A user-bound API key can read metrics only for instances owned by that user. Requests for another user's instance return `404`, as requests for a missing instance do.
</Update>

<Update label="08/10/2026">
  ## API surface finalized for release

  **Changed**

  - Production base URL is now `https://api.hivecompute.ai/v1`.
  - Staging is available at `https://staging-api.hivecompute.ai/v1`.
  - Region values are `UAE`, `FR`, and `US`.
  - Instance logs are returned newest first. `entries[0]` is the most recent line.
  - Start, stop, and terminate can return `409 Conflict` with error code `CONFLICT` when the requested action conflicts with the current lifecycle state.
  - `500` responses use the generic message `An internal error occurred.` Clients should use `error.code`, not `error.message`, for program logic.
  - `429` responses include `Retry-After` and use the standard error envelope.

  **Removed from this release**

  - `POST /ssh-keys`
  - `GET /ssh-keys/{id}`

  SSH-key operations are not backed by the released public API and will return in a later release.
</Update>

<Update label="07/29/2026">
  ## Public API documentation prepared

</Update>

## What counts as a breaking change

A breaking change may require you to update code that already works. Examples include removing an endpoint or field, changing a field type, changing authentication behavior, or making an existing request parameter required.

<Danger>
  Don't rely on undocumented fields or behavior. Build integrations against the published API reference.
</Danger>

## How to stay compatible

- Use the versioned base URL shown in the docs.
- Build logic around documented fields and `error.code` values.
- Treat cursors as opaque.
- Respect `Retry-After` on `429` responses.
- Check instance state before retrying lifecycle actions.
- Review this changelog when integration behavior changes unexpectedly.
